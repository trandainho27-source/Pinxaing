# 实体商城产品决策

用户明确要求实体物品自助下单、地址与联系方式可空、每单强制 20 元邮费、下单赠送 Telegram 通讯账号、仅展示发货状态和单号，以及统一预留微信、支付宝、USDT 接口。该要求取代原先“数字商品”的暂定方向。

## 客户购买流程

选商品 → 加入购物车 → 可选填写收货人、地址及联系方式 → 查看商品金额与不可取消的 20 元邮费 → 选择预期付款方式、同意协议 → 提交订单 → 保存订单凭证并领取赠送账号 → 查询付款与发货信息 → 联系客服或提交工单。

购买无需注册。地址和联系信息留空不阻止下单；发货前由商家与客户沟通补充。系统不会猜测或自动填写地址，也不会因资料留空免除邮费。

## 重要业务约束

- 费用使用人民币分整数：订单总额 = 数据库商品单价 × 数量之和 + 2000。客户端传入的价格、邮费或免邮参数不参与计算。
- 固定邮费以每笔订单计，一单多个商品仍为 20 元。配送区域、重量、促销与地址是否填写均不改变该规则。
- 赠送时点是创建订单成功时，并非付款后。每笔订单分配一个账号，与商品数量无关；免费赠送不进入应付金额。
- 店主导入可交付的 Telegram 账号内容，系统负责加密存储、去重与分配，不创建 Telegram 账号，也不承诺普通聊天默认端到端加密。
- 已分配账号不再回收：即使订单取消或过期，客户已见过的凭据也不能安全地转赠给另一人。
- 账号不足时不接受新订单，库存和账号分配必须同事务成功或同事务回滚。
- 未付款订单保留 30 分钟，取消或过期释放商品数量；账号仍归原订单。
- 已确认付款的数量计入已售。付款不会自动发货；店主或运营填写物流单号并确认后，配送状态才变为已发货。
- 订单配送只有 `pending`（待发货）和 `shipped`（已发货）。付款/关闭状态单独显示；取消或退款不伪造“运输中”“已签收”等物流状态。
- 商城没有物流事件查询、快递轨迹或承运商接口。
- 三个付款方式目前均不可用；保存的支付方式只表示客户选择。模拟确认付款仅存在于演示模式。

## 商家管理流程

创建分类 → 上架实体商品（一个规格一条商品）→ 登记数量库存 → 导入赠送账号 → 设置 Telegram 客服用户名 → 跟进客户订单 → 核对收款 → 补充收货资料 → 填单号并确认发货 → 售后与退款登记。

| 权限 | 店主 | 运营 | 客服 |
| --- | --- | --- | --- |
| 商品、分类、实体库存 | 是 | 是 | 否 |
| 赠送账号导入与库存 | 是 | 否 | 否 |
| 订单查看、补充收货信息、工单 | 是 | 是 | 是 |
| 确认收款、登记退款 | 是 | 否 | 否 |
| 填写单号与发货 | 是 | 是 | 否 |
| 员工、站点设置、支付设置、审计 | 是 | 否 | 否 |

赠送账号的明文不在后台列表、订单详情或操作日志中显示。客户凭订单号和密钥查看账号。订单凭证在本机记录且可下载，密钥丢失后的人工身份核验和恢复流程尚未实现。

## 升级与范围

保留原私人演示站和 GitHub 仓库，追加数据库迁移，不清空既有数据。旧数字商品不进入当前目录，原订单仍可凭密钥查看历史交付。旧支付和货源路由停止执行，相关模块保留用于历史回归，不代表现行支付已开通。

真实支付、真实商品素材、真实账号、公开营业、生产容量验证、灾备与完整安全审计仍需后续完成。当前站点保持私人演示访问范围。
